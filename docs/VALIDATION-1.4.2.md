# Lin 预填充助手 1.4.2 验收报告

## 复现的是哪一种空回？

用 SillyTavern 1.19.1 自己的浏览器发送函数和流式解析器，对同一个可按 HTTP 接收偏好选择返回格式的**本地测试端**发送相同 JSON。回复内容固定为七个字符「本地格式验证。」；唯一受测变量是浏览器声明的接收格式。两次均发出一次请求。

|条件|浏览器 Accept|测试端实际返回|酒馆读出的可见字符|
|---|---|---|---:|
|1.4.1、流式|`*/*`|整段 JSON|0|
|1.4.2、同样流式、标准档|text/event-stream|SSE|7|

这说明**接入层会按 Accept 选择格式**时，明确声明流式格式能解决一类已有响应但读不出正文的问题。未使用真实 Google 凭证，不代表用户以往的 STOP、content_filter、半句停止或所有空回都是这一个原因。对已明确指定的 Accept、无法证明可处理的请求或不理会此头的服务，不声称有改善。该头属于浏览器到酒馆这一跳，不能证明会被酒馆转发到 Google；参见 [HTTP Accept 的定义](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.1)。本轮没有增加输出上限、自动重试或自动补全。

## Google 网页搜索：请求究竟改了什么

AI Studio、Vertex 两条酒馆原生 Google 转换路径分别跑过搜索开/关、正常/已知错序和新标准开/关。本地接收端看到了酒馆转换后的 Google JSON；没有调用 Google，也没有执行任何真实搜索。[16 行逐项数据](../evidence/v142/real-142.json)同时列出浏览器和酒馆后端两侧的差异。

|标准模式下的输入|浏览器请求 JSON / 酒馆发往本地接收端的 Google JSON|搜索工具|
|---|---|---|
|搜索关；正常 / 故意调反的已知承接|相对同场景 1.4.1 均无新增差异；原有独立承接仍按旧条件处理|未添加|
|搜索开；末尾正常|两侧 JSON 均与基线相同|保留|
|搜索开；唯一可核实的相邻两条原承接错位|浏览器只有 messages 顺序不同；Google JSON 只有 contents 顺序不同。两条原文及其他字段均保留|保留；没有新增样本/标记|
|附带已有工具交互、签名、多模态、结构化输出或辨认不清|新路径跳过或撤销本次新改动；设置仍然保存|不生成或拼装替代工具结果|

判断原文相等时，对**酒馆已经完成组装的同一输入**逐条比较摘要，并断言正常顺序时浏览器 body 完全相等。它验证输入没有被改写；不能推出模型一定产生同样的故事。传输字节、正文字符和思考 token 是三个不同的统计口径。

## 复跑方式

安装插件无需开发工具。复跑验收需 Node、Python、Playwright 和 Chromium，及已安装依赖的上述 ST checkout。私有预设、模型密钥和运行中的酒馆数据不随包附送。以下环境变量中的路径由开发者自行替换；使用独立测试宿主。

```sh
npm run check
npm test
export LIN290_PRESET=/path/to/original-lin-2.9.0.json
npm test
node --test test/protocol-142.test.js
export CHROMIUM=/path/to/chromium
export LPG_ST_PATH=/path/to/SillyTavern
export LPG_BASELINE=/path/to/lin-prefill-guard-1.4.1
export LPG_EVIDENCE=/tmp/lin-prefill-guard-acceptance
npm run test:browser
npm run test:st
npm run test:acceptance
```

基线与输入 SHA-256 见 [文件校验](../evidence/v142/base-files.json)，实际分享示例见 [脱敏诊断](../evidence/v142/redacted-example.json)。各日志中的旧名字 standard/deep 有时指 **1.4.1 格式标记**，不代表新版深度实验已经启用。完整桌面、手机、已保存、跳过、回退和当前诊断截图见 [截图目录](images/v142/)；375px 主面板在 [这里](images/panel-375.png)。
